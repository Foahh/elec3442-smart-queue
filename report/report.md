# ELEC3442 Smart Queue — Project Report

Queue length and wait-time estimation from camera feeds, with an edge
Raspberry Pi running YOLO26 + ByteTrack and a multi-site Cloudflare-hosted web
dashboard.

---

## 1. Introduction

Waiting in an unpredictable queue is a small but universal annoyance. In a
canteen, a printer room, or a pop-up event booth, people have no way of
telling whether it is worth joining the line *now* or coming back in ten
minutes. The **ELEC3442 Smart Queue** project turns any ordinary Raspberry Pi
camera into a privacy-preserving "queue sensor" that reports, in real time,
three things:

1. **Queue length** — how many people are currently standing in the line.
2. **Estimated wait time** — derived from a rolling average of how long recent
   customers took to clear the zone.
3. **Comfort score** — a combined index based on the expected wait and
   environmental conditions (temperature, humidity, pressure) read from a
   Sense HAT.

Each edge node is self-contained, but when a hub URL is configured, several
nodes can federate into a single **multi-site dashboard** hosted on
Cloudflare. Users can then compare two canteens, pick the shortest queue, and
see the historical trend for the past hour or day.

---

## 2. System Overview

The system is split into three layers that communicate over HTTP:

1. **Edge inference (Pi)** — captures frames, runs YOLO26 person detection +
   ByteTrack, filters detections by a polygon "queue zone", estimates
   throughput, and writes a local SQLite time series.
2. **Hub / sync layer** — a background thread pushes a compact JSON snapshot
   of the current status to a shared web API every ~2.5 s, and pulls the
   latest status of peer sites so that every node is aware of the others.
3. **Cloudflare-hosted dashboard** — a Next.js 16 application running on
   Cloudflare Workers (via OpenNext) and backed by a Cloudflare D1 database.
   The dashboard renders site cards, a live chart, and a historical table.

![System architecture](assets/system_architecture.png)

The design separates concerns cleanly: the Pi never exposes a public HTTP
surface and is reachable only on the LAN for a local MJPEG preview, while the
public dashboard is stateless and horizontally scalable as a Worker.

## 3. Hardware and Deployment Context

| Component        | Role                                              |
|------------------|---------------------------------------------------|
| Raspberry Pi 5   | Edge compute node running `smart-queue`           |
| Pi Camera Module | `picamera2` frame source at 1280 × 720 @ 10 fps   |
| Sense HAT        | 8 × 8 LED matrix + temperature / humidity / pressure sensors |
| Cloudflare Workers | Serverless runtime hosting the Next.js dashboard |
| Cloudflare D1    | SQL database for cross-site state and history     |

Each Pi site produces inference on CPU using an **NCNN-exported** model. NCNN
is an ARM-friendly, dependency-light inference runtime ideal for Raspberry
Pi. The rest of the node stack is pure Python, managed by `uv`.

## 4. Machine Learning Pipeline

Ultralytics' export stack pins NumPy < 2.x, while the Pi runtime uses NumPy 2
(needed by current OpenCV wheels). To avoid the dependency conflict, training
and export are done in a **separate Conda environment**, and only the
resulting NCNN directory is copied onto the Pi. The pipeline is split into
three standalone scripts:

![ML pipeline](assets/ml_pipeline.png)

### 4.1 Dataset — `download_dataset.py`

CrowdHuman is fetched from Hugging Face (`sshao0516/CrowdHuman`) and exported
to Ultralytics' YOLO format:

- only the `person` class is kept; `ignore=1` annotations are filtered out;
- bounding boxes are chosen from the first available of `vbox → fbox → bbox →
  box` and converted from `xywh` (pixels) to normalised `cx cy w h`;
- both splits are written in parallel with a thread pool, producing
  `images/{train,val}/*.jpg`, `labels/{train,val}/*.txt`, and a
  `classes.txt`.

### 4.2 Fine-tuning — `finetune_yolo26.py`

`yolo26n.pt` (nano variant) is fine-tuned on CrowdHuman-person for 100
epochs, `imgsz=512`, batch 16. A minimal `crowdhuman_ultralytics.yaml`
(`nc=1`, `names: [person]`) is generated by `common.py` at runtime. The best
checkpoint is written to `results/crowdhuman_yolo26n/weights/best.pt`.

Fine-tuning on a single-class person dataset sharpens the detector for the
kind of dense, partially-occluded bodies that are typical of queues and
removes the distraction of 79 unused COCO classes.

### 4.3 NCNN export — `export_yolo26.py`

The trained `best.pt` is exported with `format=ncnn` and `int8=True`,
using the same dataset YAML for calibration. The resulting
`yolo26n_ncnn_model/` (an `.param` graph + `.bin` weights) is the only
artefact shipped to the Pi — it is roughly 3× smaller than the FP32 PyTorch
checkpoint and runs noticeably faster on CPU.

## 5. Edge Runtime (Pi)

The `smart-queue` console script is the runtime entry point
(`pi/src/main.py`). `QueueEstimatorApplication` wires up the database, hub
sync, preview HTTP server, and the camera loop.

### 5.1 Per-frame pipeline

![Frame pipeline](assets/frame_pipeline.png)

1. **Capture.** Frames come from either `PiCameraSource` (RGB888 via
   `picamera2`) or `VideoCameraSource` (OpenCV, BGR) — see
   `pi/src/camera/`. Each source reports its own `color_space` so the rest of
   the pipeline can avoid unnecessary conversions.
2. **Center square crop.** The ROI is normalised to 1:1 before inference so
   that zone polygons defined in normalised coordinates always match what
   YOLO sees.
3. **Detection.** `PersonDetector` loads the NCNN directory via Ultralytics'
   unified `YOLO` class and runs `predict(..., classes=[0])`. Only the
   person class is kept.
4. **Tracking.** Ultralytics' `BYTETracker` associates detections into
   `track_id`s; `track_buffer = camera_fps × 2` so short occlusions do not
   break identity.
5. **Zone filtering.** `QueueZone` holds a normalised polygon and uses
   `cv2.pointPolygonTest` to reject any track whose box centre falls outside
   the queue area. This is what lets the system ignore people who walk past
   the line without joining.
6. **Queue state machine.** `QueueStateTracker.update()` maintains a dict
   of `{track_id: TrackRecord}` for everyone currently in the zone. When a
   track disappears, a **`PersonEvent`** (`entry_time, exit_time,
   dwell_seconds`) is emitted — but only if the dwell is at least
   `QE_MIN_DWELL_SECONDS` (default 3 s) to filter out false positives from
   passers-by.
7. **Wait estimation.** `WaitTimeEstimator` keeps completed events in a
   `deque` pruned to a rolling 15-minute window. Throughput is
   `len(events) / window_minutes` and wait time is
   `queue_length / throughput × 60`. When throughput is zero, the estimate
   falls back to `QE_MAX_WAIT_SECONDS`.
8. **Busyness level.** Queue length is mapped to `low / medium / high` using
   the `led_green_max` and `led_yellow_max` thresholds — the same taxonomy
   drives both the Sense HAT colour and the web badge.
9. **Comfort score.** `analyzer/comfort.py` starts at 100 and subtracts a
   "wait penalty" (proportional to `wait_seconds`) plus a capped
   environmental penalty from the Discomfort Index
   `DI = T − (0.55 − 0.0055·RH)·(T − 14.5)` and pressure deviation from 1013
   hPa. The score is then labelled `comfortable / moderate / uncomfortable`.
10. **Output.** The full `QueueStatusResponse` (queue length, wait, busyness,
    comfort, latency breakdown, effective FPS) is written to `SharedState`;
    an annotated JPEG is queued to the preview encoder, and every 30 seconds
    a `QueueSnapshot` is persisted for local history.

### 5.2 Threading model

![Threads](assets/pi_threads.png)

Everything is coordinated through a small `SharedState` object (lock-guarded
mutable status + sensors + preview JPEG + connected-client count) and a
`PeerCache` keyed by `site_id`. Four threads cooperate:

- **Main thread** runs the camera loop and writes to SQLite.
- **`preview-encoder`** applies overlays (zone, boxes, HUD text), resizes and
  JPEG-encodes the latest frame. It uses ping-pong buffers so the main thread
  never blocks waiting for encoding, and it only works when at least one
  client is connected (client-count gated encoding).
- **`preview-http`** is a `ThreadingHTTPServer` serving the MJPEG stream on
  `QE_API_HOST:QE_API_PORT/preview`.
- **`hub-sync`** batches pushes and pulls to the web app.

### 5.3 Sense HAT output

`SenseHATDisplay.show_sites()` renders the local site and all live peers on
the 8 × 8 LED matrix, partitioned into horizontal bands of equal height.
Within a band, the number of lit columns is `queue_length / queue_max × 8`.
Stale peers (see §6) go blue. This gives a pocket-sized physical dashboard
that anyone in the room can glance at.

## 6. Hub Sync Protocol

![Hub sync sequence](assets/hub_sync_sequence.png)

The hub sync is deliberately dumb and stateless. It runs in one background
thread and uses only the Python standard library (`urllib`), so there are no
new dependencies on the Pi.

**Push** (`POST /api/ingest`):

- sent every `QE_HUB_PUSH_INTERVAL` seconds (default 2.5 s);
- body contains `site_id`, `display_name`, optional `latitude / longitude`,
  current queue state, comfort score, an embedded `snapshot`, and the latest
  sensor reading;
- authenticated with a shared secret via the `X-Api-Key` header, checked
  against the Cloudflare secret `API_KEY`;
- exponential backoff (doubling, capped at 60 s) on any non-200 or network
  error, reset to the configured interval after a successful push.

**Pull** (`GET /api/sites`):

- polled every `QE_HUB_PULL_INTERVAL` seconds; the result is stored in
  `PeerCache` and also mirrored into the local SQLite `PeerSiteSnapshot`
  table so the node can remember peers across restarts;
- `stale` is *recomputed* on read — a snapshot is considered stale after 30 s
  without a successful pull, so the Sense HAT turns a site blue instead of
  showing outdated colours.

Because both legs are time-independent, any node can drop off the network and
the others keep working; when it comes back, the hub's latest-write wins.

## 7. Data Model

![Data model](assets/data_model.png)

Two storage layers coexist:

### 7.1 On-device (SQLite via SQLModel)

`QueueSnapshot` is the canonical local time series, written twice per minute
(`snapshots_per_minute=2`). `PersonEvent` records individual exits and is the
source of truth for throughput. `PeerSiteSnapshot` is a local mirror of the
hub's latest view of other sites.

### 7.2 Cloudflare D1

Two tables, created by `migrations/0001_initial.sql`:

- **`site_status`** — one row per site, UPSERTed on every ingest; this is
  what `/api/sites` and the dashboard cards read.
- **`site_snapshots`** — append-only time series behind `/api/history`,
  indexed on `(site_id, timestamp)`.

Separating "latest" from "history" keeps the dashboard's landing-page query
to a single small table scan, while the chart and history tab pull from the
larger snapshots table with a bounded time window.

## 8. Web Dashboard

The web app lives in `web/` and is a standard Next.js 16 + React 19 project
adapted for the edge with `@opennextjs/cloudflare`. Key pieces:

- **API routes** (`web/app/api/`):
  - `POST /api/ingest` — authenticated endpoint the Pis push to; wraps the
    write in `upsertSiteStatus` + `insertSiteSnapshot`.
  - `GET /api/sites` — public listing of all sites, used by both the browser
    and every peer Pi.
  - `GET /api/history?site_id=...&minutes=...` — bounded snapshot query.
- **`DashboardShell`** — the client component that polls `/api/sites` via
  TanStack Query, tracks the selected site, and lazy-loads the trend chart
  (`QueueChart`, Recharts) and the `HistorySection` via `next/dynamic` to
  keep the initial bundle lean.
- **`SiteCard`** — presents queue length, wait time, comfort score + emoji,
  and the environmental pills (T / RH / P). Freshness is shown as a "Live"
  or "Offline" badge derived from the `stale` flag.
- **Styling** — Tailwind v4 + shadcn/ui components, theme-aware via
  `next-themes`.

The dashboard is stateless: every render is a pure function of the two D1
queries, so a failed Cloudflare Worker invocation is trivially retried.

## 9. Configuration Surface

The Pi is configured entirely through environment variables (prefix `QE_`)
loaded via `pydantic_settings`. The most relevant groups are:

| Area              | Keys (abbrev.)                                              |
|-------------------|-------------------------------------------------------------|
| YOLO              | `YOLO_MODEL_PATH`, `YOLO_CONFIDENCE`, `YOLO_IOU`, `YOLO_IMGSZ`, `YOLO_DEVICE` |
| Camera            | `CAMERA_SOURCE` (`picamera`/`video`), `CAMERA_VIDEO_PATH`, `CAMERA_WIDTH`, `CAMERA_HEIGHT`, `CAMERA_FPS` |
| Queue zone        | `QUEUE_ZONE` (normalised polygon)                           |
| Estimation        | `THROUGHPUT_WINDOW_MINUTES`, `MIN_DWELL_SECONDS`, `SNAPSHOTS_PER_MINUTE`, `MAX_WAIT_SECONDS` |
| LED thresholds    | `LED_GREEN_MAX`, `LED_YELLOW_MAX`, `QUEUE_MAX_DISPLAY`      |
| Hub sync          | `HUB_URL`, `HUB_API_KEY`, `SITE_ID`, `SITE_DISPLAY_NAME`, `SITE_LATITUDE/LONGITUDE`, `HUB_PUSH_INTERVAL`, `HUB_PULL_INTERVAL` |
| Preview server    | `API_HOST`, `API_PORT`, `PREVIEW_ENABLED/FPS/WIDTH/HEIGHT/JPEG_QUALITY` |
| Persistence       | `DATABASE_URL`                                              |

Single-site and multi-site deployments use the exact same binary; hub sync
stays off when `QE_HUB_URL` is empty.

## 10. Discussion and Design Rationale

**Why track identities instead of counting boxes per frame?**  A per-frame
box count would double-count anyone who stayed in line for more than one
frame; ByteTrack associates detections into durable identities, which both
reduces noise and unlocks the dwell-time measurement that throughput
estimation needs.

**Why a rolling window instead of instantaneous throughput?** A single
person leaving the queue adds a large spike to any short-horizon rate
estimate. A 15-minute window smooths this out without hiding genuine changes
in service speed.

**Why NCNN instead of ONNX Runtime or TorchScript?** NCNN is the most
frugal option on 64-bit ARM CPUs, and its INT8 export roughly halves latency
compared to the FP32 graph without a meaningful accuracy hit for this
single-class, close-range task.

**Why Cloudflare Workers + D1?** The hub's job is essentially two SQL
statements per ingest and one SELECT per pull. Workers give a generous free
tier, zero cold-start on D1 reads, and a globally distributed edge, which
matches the "many dumb sensors" topology of the project.

**Privacy.** Raw frames never leave the Pi; only aggregated counts, wait
estimates, and optional environmental readings are pushed. The local MJPEG
preview is intentionally bound to `QE_API_HOST` (default `0.0.0.0`) but
should be firewalled to the LAN in production.

## 11. Limitations and Future Work

- **Single monocular camera.** The zone polygon must be tuned manually per
  install; a fisheye or wide-angle lens skews the polygon-in-image mapping.
  A future version could support camera calibration and ground-plane
  homography.
- **Person-only fine-tune.** CrowdHuman emphasises crowded bodies but under-
  represents children, heavy occlusion by trays, and unusual camera angles.
  Collecting a small site-specific finetune set would improve recall.
- **Wait-time prior.** The estimator is memoryless between runs; historical
  snapshots are stored but not yet used to bootstrap throughput after
  restart. A simple time-of-day prior would help during the first few
  minutes.
- **No alerting.** The dashboard could easily gain a threshold-based webhook
  or push notification (e.g. "queue > 10 for > 5 min") using the same D1
  time series.
- **Authentication on the preview server.** The MJPEG endpoint is currently
  unauthenticated; adding a shared token or mTLS would make it safe to
  expose beyond the LAN.

## 13. Summary

Smart Queue demonstrates how a modest embedded platform — a Raspberry Pi
with a camera and a Sense HAT — can be turned into a useful real-world
sensor when paired with a tight computer-vision pipeline (YOLO26 +
ByteTrack), a thoughtful estimator (rolling throughput, zone-aware tracking,
dwell filtering), and a lightweight edge-hosted dashboard. The separation
between a self-sufficient edge node and a thin, stateless hub means the
system degrades gracefully: each Pi remains useful on its own, and the
dashboard simply loses rows when a site drops off.
